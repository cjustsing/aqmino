# 水序首版提醒规则

版本：v0.1｜日期：2026-10-10｜关联：[功能方案](product-design.md)、[交互设计](../design/macos/interaction-design.md)、[技术设计](technical-design.md)。

本文件是提醒行为的统一依据。`I` 表示提醒间隔，默认 45 分钟；时段采用设备当前时区与用户选定的星期。用户设置的间隔是实际经过的分钟数。

## 1. 调度方式与产品边界

首版应用常驻菜单栏。应用内只维持一个下一次唤醒任务，到期时检查规则，再请求系统展示本地通知；不提前向系统提交整天的重复提醒。

使用 `UNNotificationRequest` 的即时请求：`trigger` 为 `nil`。这一能力有[Apple 官方说明](https://developer.apple.com/documentation/usernotifications/unnotificationrequest/init(identifier:content:trigger:))。这是本应用的实现选择，便于在每次发出前重新判断暂停、目标和工作时段。

关闭面板不停止调度；退出或进程结束后不创建新的提醒。已经交给系统的通知可能受用户设置延迟展示，应用无法承诺精确交付时间。[User Notifications](https://developer.apple.com/documentation/usernotifications/)明确说明交付不保证及时。

## 2. 时段与日期

- 星期对外按周一至周日表达，至少选一天。
- 每天一个同日时段：`start < end`，时段长度必须大于 `I`。
- 时段采用 `[start, end)`，到结束时刻不再产生新提醒。
- 首版不支持跨夜时段；表单说明并阻止无效输入。
- 当前时区下的本地日期决定「今日」。记录按时间戳是否属于该日期的日历区间统计。
- 下一天使用日历运算，不将一天固定为 24 小时。时区变化会重新统计今日数据。
- 夏令时不存在的钟面时间取当天其后第一个有效时间；重复钟面时间取第一次出现。间隔仍按实际时长计算。

`windowID` 由本地日期、时区标识及时段设置构成。改变它时，旧周期不继续作为新时段的计时基准。

## 3. 提醒资格与状态

资格由多个条件共同决定。界面主状态按以下顺序展示，通知能力问题可以作为附加说明保留。

| 优先级 | 条件 | 状态与行为 |
| --- | --- | --- |
| 1 | 数据无法可靠读取或写入 | 暂停调度，保留可读取的状态，提供重试 / 恢复入口 |
| 2 | 全局提醒开关关闭 | 「提醒已关闭」，记录照常可用 |
| 3 | 设备睡眠或用户会话已切出 | 停止应用调度，恢复事件后重新判断 |
| 4 | 自定目标已达成且开启达标停止 | 「今日提醒已完成」，等待下一个本地日期 |
| 5 | 有效暂停 | 展示恢复时间或「今日已暂停」 |
| 6 | 不在选定星期或时段 | 展示下一有效时段的计划时间 |
| 7 | 通知尚未开启或被拒绝 | 展示开启 / 前往设置入口，不向系统发通知 |
| 8 | 有有效的稍后时间 | 「稍后提醒：HH:mm」 |
| 9 | 正常计时 | 「下一次提醒：HH:mm」 |

授权但横幅关闭、通知中心仍开启时，可向通知中心交付并展示「提醒将显示在通知中心」。系统专注模式可能影响展示；首版不推测专注状态，也不申请高优先级提醒。依据：[通知权限](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)、[通知管理](https://developer.apple.com/design/human-interface-guidelines/managing-notifications)。

## 4. 正常周期算法

1. 先根据当前状态检查资格，再取得当前或下一个有效时段。
2. 应用已在时段开始前运行：当前时段初始基准为 `start`，第一次提醒为 `start + I`。
3. 在时段内首次启用、恢复，或启动时没有未来有效周期：基准为 `now`，候选时间为 `now + I`。
4. 记录当下饮水成功：基准更新为该记录时刻，清除稍后状态。有效暂停与全局关闭保持不变。
5. 候选时间必须落在当前时段内；否则进入下一有效时段，其首次时间为 `nextStart + I`。
6. 到期时再次检查状态、时段、时区、通知能力和调度代次；有效且迟到不超过 60 秒才产生一个新提醒机会。
7. 调度迟到超过 60 秒时，从 `now` 重新计时，不补发错过机会。睡眠、会话恢复和冷启动不使用这段宽限，统一走恢复规则。
8. 本次正常机会结束后，以实际处理时刻重新计算 `now + I`。不按错过的旧时间连续追赶。

`generation` 表示当前调度代次。重新计时、暂停、设置变化和退出等使旧任务失效的事件都增加代次。异步任务在提交前检查代次，旧任务直接结束。

## 5. 事件转换

| 事件 | 状态处理 | 下一次时间 |
| --- | --- | --- |
| 快捷 / 自定义记录成功 | 更新记录、累计、最近容量；清除稍后；保留暂停 | 具备资格时从记录时刻 + `I`，受时段与目标约束 |
| 正常提醒被处理 | 生成一次机会，清理本应用旧提醒；不增加饮水记录 | 实际处理时刻 + `I`，或下一有效时段 |
| 暂停 30 分钟 / 1 小时 | 保存绝对截止时间，清除稍后，取消当前任务 | 到期后重新经过 `I`；超出时段则等待下一时段 |
| 今日不再提醒 | 保存本地日期暂停标识，清除稍后 | 当本地日期变化后解除，按下一有效时段计算 |
| 手动恢复 | 清除暂停与稍后，重新建立基准 | 时段内 `now + I`，时段外 `nextStart + I` |
| 有效通知的「10 分钟后」 | 消费本次动作，设置单次稍后时间 | `now + 10 分钟`，超出时段时改为 `nextStart + I` |
| 用户未响应 / 关闭通知 | 不记录饮水，不延后，不改变频率 | 保持正常下一次计划 |
| 更改星期、时段、间隔 | 保存后清除稍后，重新计算；暂停仍有效 | 时段内 `now + I`，时段外 `nextStart + I` |
| 关闭 / 开启提醒 | 关闭清除稍后并停止；开启保留尚有效的暂停 | 开启且具备资格后经过完整间隔 |
| 达到目标且开启停止 | 清除稍后，停止当天周期 | 下一本地日期、有效时段首次时间 |
| 删除记录或调整目标后不再达标 | 更新统计；若此前被目标停止则重新开始 | `now + I`，受其他条件约束 |
| 下一本地日期 | 更新今日汇总，清除过期的今日暂停和旧时段周期 | 新有效时段首次为 `start + I` |
| 系统时区 / 时间变化 | 校验时区、日历区间与周期；有效未来计划与稍后保留，不补发过期机会 | 有效则保持原时间；无效或过期则 `now + I`，受时段限制 |
| 睡眠 / 会话切出 | 取消应用计时，清理本应用已展示提醒 | 暂不创建新机会 |
| 唤醒 / 会话恢复 | 重新检查暂停、目标与原计划；取消旧计时器后恢复有效计划 | 有效则保持原时间；已过期则 `now + I`，不补发 |
| 冷启动 | 先处理已收到的通知动作；再恢复偏好与未来有效周期 | 有未来有效时间则保留；已过期则 `now + I` |
| 通知权限重新具备 | 重新检查实际展示能力，重新计时 | 经过完整间隔，不立即补发 |
| 退出 | 取消计时及本应用通知清理工作，保存已提交状态 | 下一次启动时判断 |
| 删除全部记录 | 清空记录与撤销，失效所有旧未消费机会，保留偏好 | 清除稍后并从 `now + I` 重新计时，受暂停与时段限制 |

冷启动、唤醒和系统校时使用同一恢复规则：未来计划的时区、时段和间隔必须匹配，且提醒时间落在启用的星期与时段内。时段内的计划允许一个完整间隔，并额外容许 60 秒的向后校时偏差，避免刚建立周期时因小幅校时重新计时；有效的 10 分钟稍后计划同样保留。时段外或跨日、跨周末的 `nextStart + I` 计划也可保留。过期、过远或不匹配的计划重新计时，恢复路径不使用正常计时器的 60 秒迟到宽限，也不生成旧提醒机会。仍有效的暂停与目标停止优先。

恢复时取消旧平台计时器并更新环境代次；保留未来计划时不改变业务周期代次、基准和稍后时间。旧计时器与旧环境排队的到期回调不能补发提醒。

定时暂停按实际时长，到期时在时段内以暂停截止时间为恢复基准；若应用睡眠、退出或任务过期，恢复事件的基准改为实际恢复时刻。今日暂停以日期标识匹配，日期改变后解除并移除，不会因之后时区回退重新生效。

删除一般记录只修改统计，不重置正在正常计时的周期。10 秒内的「撤销刚才记录」会在没有后续调度事件时恢复记录前的基准；恢复后的时间已过去则从撤销时刻重新计时。有后续事件时仅撤销记录，保持较新的周期。达标资格变化始终重新评估。

## 6. 通知机会、动作与去重

- 每次机会使用独立 `occurrenceID`，附带发送时的明确记录容量与创建时间。开始交付前先保存机会标记及下一周期，避免重启时重复提交。机会的交互代次对应这次周期推进后的代次，后续事件才使其稍后动作失效。
- 「记录 250 ml」在动作处理时刻创建记录，使用按钮原本表示的容量。设置变化不改变旧按钮的含义。
- 通知正文点击只打开面板；关闭或忽略通知不创建饮水记录。
- 同一机会的业务动作最多消费一次，消费标记与对应记录 / 稍后状态一次保存。重复回调返回已处理结果；删除记录不删除消费标记。
- 「记录」可以作用于已知、尚未消费且未因数据清空失效的旧机会，按当前时刻记录；「稍后」只接受当前机会且期间没有更新周期的有效动作。失效动作打开面板展示当前状态，不改变计划。
- 未知或缺失本地机会数据的动作不直接创建记录，打开面板让用户明确操作。
- 面板或任一水序窗口处于前台可见状态时，到期只显示应用内的一次提醒说明，不再重复展示系统横幅；这次机会仍进入正常下一周期。仅有后台窗口不触发这一替代行为。
- 无通知权限时不交付系统通知；面板可展示到点状态和开启通知入口。应用检查计划时仍会刷新权限，不把这段时间作为待补发队列。
- 普通提醒每次尽力移除本应用先前的已交付提醒，最多保留一条当前提醒。测试通知使用独立标识，不改变记录和周期。
- 交付失败不自动连续重试，显示失败状态并保留正常下一周期；用户可以发送测试通知。重复使用已交付通知的标识可能再次触发提示，因此去重依赖本地机会标记。[Apple 请求标识行为](https://developer.apple.com/documentation/usernotifications/unnotificationrequest/init(identifier:content:trigger:))

清理只作用于水序拥有的通知标识。清理与系统展示可能存在竞争，已经交给系统的消息仍可能迟到；应用不以发送成功推断用户已经看到或喝水。

## 7. 可复现的规则验证例子

以下例子默认工作日 09:00–18:00、`I = 45 分钟`，无目标限制，通知可用。规则测试输入固定时间、时区及事件，不依赖测试机器的当前时间。

| 编号 | 输入 / 事件 | 期望 |
| --- | --- | --- |
| T-01 | 周一 08:50 应用运行 | 第一次为 09:45 |
| T-02 | 周一 10:00 首次启用 | 下一次为 10:45 |
| T-03 | 原定 10:45，10:20 记录 250 ml | 下一次为 11:05，今日增加 250 ml |
| T-04 | 10:00 暂停 30 分钟，应用持续运行 | 暂停至 10:30，下一次 11:15 |
| T-05 | 10:00 提醒，10:02 选择稍后 | 10:12 再提醒，其后从实际处理时刻经过 45 分钟 |
| T-06 | 17:30 记录 | 当日不再提醒，下一有效工作日 09:45 |
| T-07 | 到期处理时为 18:00 | 不提交通知，进入下一有效时段 |
| T-08 | 周五今日暂停，周六应用运行 | 今日暂停解除；默认下一次周一 09:45 |
| T-09 | 原定 10:45，10:40 睡眠，11:00 唤醒 | 11:45，不补发 10:45 |
| T-10 | 10:45 到期，应用任务迟到至 10:47 | 跳过该机会，下一次 11:32 |
| T-11 | 达标停止开启，记录后达到目标 | 当日停止；删除后低于目标则从删除时刻重新计时 |
| T-12 | 同一通知记录动作被回调两次 | 仅一条记录、一次累计、一个动作消费标记 |
| T-13 | 暂停时记录饮水；随后点击旧通知稍后 | 记录保存；暂停保持；旧稍后不改变状态 |
| T-14 | 无通知权限，用户记录后重新开启权限 | 记录正常；权限恢复后完整间隔再提醒 |
| T-15 | 冷启动：未来有效时间 / 已过期时间 | 前者保留，后者重新计时；均不重复产生旧机会 |
| T-16 | 时区跨日本地日期变化 | 今日汇总按新日历区间重算，今日暂停重评估 |
| T-17 | 夏令时日期、重复或不存在的时段边界 | 日历策略确定一个有效边界，无固定 24 小时假设 |
| T-18 | 通知交付失败 / 机会标记保存失败 | 前者不连续重试；后者停止调度并显示数据问题 |
| T-19 | 菜单栏面板可见且提醒到期 | 一次应用内提醒，不叠加系统横幅 |
| T-20 | 记录撤销前没有 / 已有后续调度事件 | 前者恢复旧基准并防止过期补发；后者保留新周期 |
| T-21 | 原定 09:45，09:22 / 09:38 连续小幅校时或唤醒 | 仍为 09:45；周期与有效稍后时间保留 |
| T-22 | 恢复时刚好到期或仅错过 1 秒 | 跳过旧机会，从恢复时刻经过完整间隔；不使用迟到宽限 |
| T-23 | 跨夜 / 周末保存的首次 09:45 计划，09:22 恢复 | 仍为当日 09:45；时区或时段不匹配时重新计算 |

固定时间与日历规则由核心测试覆盖；启动队列由 AppModel 检查覆盖；系统事件接线与计时器竞争由隔离的原生恢复检查覆盖。
