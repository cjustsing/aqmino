# 水序首版技术设计与验收

版本：v0.1｜日期：2026-10-10｜依据：[产品方案](product-design.md)、[提醒规则](reminder-rules.md)、[交互设计](../design/macos/interaction-design.md)、[目录架构](architecture.md)。

本次为 standalone 编码前设计，行为文件采用 report-only。当前没有源码、构建清单、配置或测试；只创建方案并更新文档入口。

## 1. 技术选择与兼容性

| 部分 | 选择 | 理由与约束 |
| --- | --- | --- |
| 应用 | macOS 13+，SwiftUI 为主，必要的 AppKit 适配 | 对应原生菜单栏产品；API 使用需满足最低系统版本 |
| 菜单栏 | 优先 `MenuBarExtra` 的 window 样式 | 适合轻量面板；M1 验证公开窗口观察与交互能力 |
| 窗口 | 公开 SwiftUI / AppKit 窗口路由，已有窗口优先聚焦 | 验证设置、记录窗口与面板之间的焦点行为 |
| 核心逻辑 | 单个本地 `AqminoCore` library target | 规则独立于 UI、系统通知和存储框架 |
| 数据 | Codable 版本化 JSON 快照、串行保存、原子替换 | 适合首版个人记录规模，减少存储依赖；规模增长后再评估迁移 |
| 通知 | UserNotifications，应用到期后即时交付 | 当前资格检查发生在交付前，退出后不继续应用周期 |
| 登录启动 | `SMAppService.mainApp`，读取实际状态 | 用户主动启用；系统批准情况由界面反映 |
| 系统事件 | AppKit / Foundation 的公开事件 | 睡眠、唤醒、会话、时区、系统时间和日期重评估 |
| 依赖 | 初期不引入第三方运行时依赖 | 系统能力与单一核心包已经覆盖首版 |

`MenuBarExtra` 从 macOS 13 可用，[Apple 文档](https://developer.apple.com/documentation/swiftui/menubarextra)及本机 SDK 声明已经核对。`SettingsLink` 从 macOS 14 才可用，最低版本实现不得无条件使用它；设置入口采用公开的自有窗口路由。

若 M1 无法用公开接口可靠观察 MenuBarExtra 的前台可见状态，则切换为 `NSStatusItem + NSPopover` 承载同一 SwiftUI 面板。选择在 M1 固定，业务与规则接口不受影响。

睡眠事件通过 `NSWorkspace.shared.notificationCenter` 观察，参见 [willSleepNotification](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification)。登录启动参见 [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)、[mainApp](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp)。

## 3. 数据模型

| 类型 | 核心字段 | 约束 |
| --- | --- | --- |
| `HydrationRecord` | `id`、`operationID`、`amountMl`、`recordedAt`、`timeZoneIDAtCreation`、`source`、可选 `occurrenceID` | ml 为整数；首版只记录当前时刻；来源为快捷、自定义或通知 |
| `ReminderPreferences` | 开关、ISO 星期集合、起止分钟、间隔、三个容量、最近容量、可选目标、达标停止、声音、引导完成 | 由核心层校验；登录启动实际状态从系统读取 |
| `ReminderRuntime` | 当前时段标识、周期基准、下一次计划、暂停模式、稍后时间、调度代次、最近机会标识 | 稍后与暂停边界遵循提醒规格；重启不重放过期周期 |
| `ReminderOccurrence` | 标识、创建时刻、按钮容量、交互代次、交付结果、消费或失效标记 | 一次业务动作最多消费一次；仅当前有效机会允许稍后 |
| `CommandReceipt` | 操作标识、结果类别与关联标识 | 为提交重试提供幂等依据；不依赖 UI 按钮禁用作为唯一去重 |
| `UndoToken`（仅内存） | 最近操作的记录内容、旧周期、操作后代次、10 秒截止时间 | 最近一次覆盖前一次；新调度事件只保留记录撤销能力；退出或全部删除时清除 |
| `StateSnapshot` | `schemaVersion = 1`、修订号、偏好、记录、运行状态、机会与操作回执 | 整体串行保存，保证记录、动作消费与周期一致 |

内部时间使用 `Date` 表示瞬时；序列化采用带毫秒的 UTC ISO 8601 字符串，时区单独用 IANA 标识。星期采用周一为 1、周日为 7 的显式约定，适配 Foundation 的星期值时进行转换。

「今日」使用设备当前时区的日历日区间查询时间戳。记录创建时区保留供后续上下文展示，不能固定替代当前日期归属。进度为 `min(今日总量 / 目标, 1)`，展示总量不截断。

先保留所有记录，首版界面只展示今日。格式升级必须读取旧版本、验证转换、备份并成功保存后切换；遇到更新的未知版本进入只读错误状态，不覆盖文件。跨语言交换格式在导出或第二个平台立项时从这些语义建立独立契约。

## 4. 写入、恢复与删除

保存位置通过系统 Application Support API 获取，再放入应用自己的 `Aqmino/` 目录；沙箱与直接分发均使用平台提供的位置，不硬编码用户主目录。

所有命令由一个串行协调器处理：校验 → 用已确认快照计算候选状态 → 保存候选快照 → 更新已确认状态 → 发布 UI → 执行对应系统效果。写入失败时不显示成功、不累计、不提前执行新的提醒计划。

协调器使用命令队列与单一处理循环；即使以 actor 实现，异步写入等待期间的新命令也只入队，避免 actor 重入造成并行读改写。通知系统效果在已确认状态之外异步执行，权限查询后、实际提交前再次校验最新调度代次。

主文件预定为 `state-v1.json`，采用临时文件与原子替换。更新前保存最近一次有效快照为备份；快照修订号用于检查读写和恢复结果。备份更新失败也应保留现有主文件并报告保存失败。

加载时先检查删除意图，有有效意图则进入删除恢复；意图无法解析或版本未知时进入错误状态。没有意图时才按下表读取普通快照。

| 读取情况 | 处理 |
| --- | --- |
| 主文件有效 | 正常加载，检查结构与版本 |
| 首次使用且主文件与备份均不存在 | 创建默认状态，用户保存首个偏好 / 记录后落盘 |
| 主文件损坏或缺失、备份有效 | 保留已有文件，界面提示可恢复备份；用户选择恢复后再替换主文件并重新计时 |
| 两者均无效或版本过新 | 保留文件，停止调度与写操作，提供重新读取或查看数据位置 |
| 磁盘写入失败 | 保持上次已确认状态，展示重试入口 |

单条删除可撤销；撤销仍需成功保存才更新 UI。一次只提供最近可撤销操作，后续操作取代旧撤销入口。删除全部记录需确认，清除记录、恢复副本和内存撤销内容，保留偏好并重新计时。旧未消费通知机会全部失效，只保留防重放所需的最小标识；旧通知无法通过残留副本恢复删除前的记录。

为避免删除后备份恢复出旧记录，删除全部记录采用可恢复的删除事务：先原子写入带清空后有效快照与修订号的删除意图，清理包含旧记录的备份和应用生成的损坏文件副本，再原子提交清空记录的主快照，最后清理意图。意图存在时启动恢复只完成该删除，不回滚到旧记录；写入意图成功即进入待完成删除状态，界面不得再报告旧快照可写。只有全过程完成后显示删除成功。此路径需要注入各步骤失败验证。

通知提交前先保存本次机会标记和下一周期。应用崩溃在保存和提交之间时允许错过一次提醒，冷启动不会重复提交旧机会。通知动作的记录、消费标记、容量偏好和新周期则一次保存，失败后可用同一动作标识重试。

## 5. 系统能力适配

- 通知类别提供明确容量的记录动作与稍后动作。授权请求只由用户的开启操作触发；打开面板、返回设置与计划检查时刷新权限，交付前再读取实际设置。
- 动态容量使用稳定的类别标识，如 `water.amount.250`；同一标识的动作文案不随之后的容量设置变更。恢复仍可处理机会所需的类别，确保旧按钮文案与本地机会保存的容量一致；M1 验证系统实际展示。
- 正常通知采用普通中断级别，声音按本应用与系统设置共同决定。发送测试使用独立标识与节流，不修改业务周期。
- 当前前台可见的水序 UI 到期时显示应用内提示；窗口观察以公开接口为准，在 M1 验证。面板关闭后恢复普通交付方式。
- 调度使用一个可取消任务，等待过程中减少无谓唤醒；回调验证代次与当前时间，避免旧任务提交。分钟显示只在面板可见时更新。
- 系统恢复事件取消旧计时器后校验原计划；重启、唤醒和小幅校时保留有效的未来时间与稍后状态，过期机会跳过且不补发。业务周期代次与平台环境代次分别控制计划有效性和旧回调失效。冷启动先处理通知动作再恢复正常调度。主动退出取消调度，并清理本应用拥有的通知。
- 登录启动 UI 读取 `SMAppService` 状态，注册失败或需要批准时给出系统设置入口，不先把开关显示成成功。
- 日志只记录事件类型、匿名操作标识及错误类别，不记录完整用户快照；本地记录功能不需要网络。

## 7. 风险与验证关口

| 编号 | 影响 / 发现方式 | 处理与覆盖 |
| --- | --- | --- |
| RISK-01 | 系统可延迟或抑制通知，发送成功不能说明用户已看到 | 显示计划与实际能力，普通提醒，不追赶；AC-04、AC-05、AC-18 |
| RISK-02 | 写入失败、备份损坏或并发操作导致状态不一致 | 串行命令、原子快照、恢复入口、删除事务；AC-09、AC-14、AC-15 |
| RISK-03 | 日期与时区处理造成重复或错误累计 | 日历区间、明确边界、固定时区样例；AC-06、AC-12 |
| RISK-04 | 重复通知动作、旧任务回调重复记录或提醒 | 持久回执、机会消费、代次检查；AC-10、AC-13 |
| RISK-05 | 用户退出后预期仍会提醒，或登录启动未真正成功 | 产品说明和真实状态，验证关闭面板与退出差异；AC-01、AC-16 |
| RISK-06 | 最低系统版本上的菜单栏 / 窗口路由与前台判断存在差异 | M1 做能力验证，公开 AppKit 方案兜底；AC-01、AC-02、AC-17、AC-18 |

M1 必须验证菜单栏、窗口、通知动作冷启动、睡眠事件与登录启动。能力验证失败时先调整适配层和对应设计；通过后再进入记录与提醒主体开发。发布前覆盖最低系统版本与当前系统，并验证计划支持的硬件架构。

Bundle ID、签名团队、发布渠道及最终应用图标是工程 / 发布阶段的待填项。首版的功能和规则没有因此保持未定义。
